# LIJOX

An open, permissionless registry protocol for Lightning service providers (LSPs), and the registry worker that implements it. Wallets built on it — [Lightning in a Jar](https://github.com/dav1dpgit/lightninginajar) is the first — discover LSPs from one or more registries, connect to the one they choose, and switch. Operators run the LSP side with the [LIJOX adapter](https://github.com/dav1dpgit/lijox-lnd-adapter) on their existing LND node.

LIJOX is not a federation. Anyone can publish a registry; wallets aggregate across registries on their own; the only discipline is the market — fees and behaviour, not membership. An LSP that participates serves any wallet that speaks the standard.

**Status: registry worker 0.25.0. One live registry, run by the standard's author, reached at two addresses that serve the same records: the Cloudflare worker (`lij-worker.dp-a95.workers.dev`) and the same code running on the author's own node, reached directly with no Cloudflare in between (`registry.lightninginajar.xyz`). Three registered LSPs: two run by the standard's author, and one, since 2026-11-19, by an independent operator on his own Start9 node.** That concentration is stated in the wallet's README as well; it changes as other operators register.

## The registry worker — routes

| route | who calls it | what it does |
|---|---|---|
| `GET /lsps` | wallets | the registry: name, endpoint, WSS URL, fees, channel limits, capabilities per LSP, plus `last_seen_ms`, `first_registered_at` and `stale` (no registration for 24 h — adapters ≥0.71 re-register every 6 h); and (0.8.0) `filter_url` / `filter_sp` — the provider's own block-filter server, if it offers one, and whether that server serves the silent-payment tweak index (`null` / `false` when none: wallets read the default server); (0.13.0) `routes` — the provider's connection routes (its API, WebSocket and block-filter addresses) and which of them pass through Cloudflare; (0.21.0) `tower` — whether the provider runs a watchtower for wallets, and its terms; (0.22.0) `chan_confs` — the confirmations the provider's LND asks for before a channel a wallet funds can be used; (0.24.0) `rpc` — the request forms the provider takes inside the Lightning connection (today one word, `lsps0`; which methods it serves there a wallet asks the provider itself, inside the connection). (0.25.0) Each record is served with the `signature` and `ts` it was registered with: a wallet rebuilds the signed text from the record as served and checks the provider's signature itself, so a record changed after signing — by the registry or by anything in the way — is not used. (Until 0.24.0 the two were checked on the way in and stripped on the way out.) |
| `POST /lsps/register` | LSPs | `lijox-register:v1`, `v2` (the provider's block-filter server, 0.8.0), `v3` (the Tatara pool block, 0.11.0) `v4` (the `routes` list, 0.13.0), `v5` (the `tower` block, 0.21.0), `v6` (the `chan_confs` block, 0.22.0) or `v7` (the `rpc` list, 0.24.0) — the message versioned by which fields are present — the LSP signs its full advertised field set plus a timestamp with its node key (LND `signmessage`); the worker verifies by public-key recovery, ±600 s. A record that offers a block-filter server (0.8.0) is signed as `lijox-register:v2`: the v1 fields plus `filter_url` (https only — a host, an optional port and path, no trailing slash, 200 characters at most) and `filter_sp`; a record without one stays v1 byte for byte, so older adapters register unchanged, and neither signature verifies against the other's field set. A record that offers Tatara pools (0.11.0) is signed as `lijox-register:v3`: the v2 fields (`filter_url` empty when none) plus the `tatara` block's fields in a fixed order (lists comma-joined, booleans `1`/`0`); the block is served to wallets as declared; stripping, adding or changing it changes the message, so no signature verifies against another's field set. A record that lists its connection routes (0.13.0) is signed as `lijox-register:v4`: the v3 fields (`filter_url` empty and the tatara fields empty / `0` when there is no block) plus one field holding every route as `reach|endpoint|wss_url|filter_url`, routes joined by `;` — 1 to 3 routes, each exactly `{reach, endpoint, wss_url, filter_url}`, `reach` one of `direct`, `cloudflare`, `tor`, no two routes with one endpoint; the first route must repeat the record's own `endpoint`, `wss_url` and `filter_url` (what older wallets read), or the registration is refused. `GET /lsps` serves `routes` as stored; a wallet picks its route by its own preference. A record that states a watchtower (0.21.0) is signed as `lijox-register:v5`: the v4 fields plus `tower` — `offered`, `quota_bytes`, `keep_days_silent`, `form` — in that order. A record that states its confirmations (0.22.0) is signed as `lijox-register:v6`: the v5 fields plus `chan_confs: {min, max}` (whole numbers from 1 to 144, min not above max). A record that states which request forms it takes inside the Lightning connection (0.24.0) is signed as `lijox-register:v7`: every v6 field in place (the two `chan_confs` fields as `0` where the record has none) plus one field, the `rpc` words joined by `,` — a list of 1 to 4 different words, each 1 to 16 lowercase letters or digits; a record without the list signs as before. An adapter that meets an older registry sends the record without the newer block, signed at the lower version. Registry writes are limited to 60 a minute per address, other writes to 300 (0.16.0). |
| `POST /lsps/unregister` | LSPs | `lijox-unregister:v1` (0.6.0) — a signed departure (pubkey + ts); the ts must be newer than the current registration's, so a captured request cannot be replayed against a later re-registration. The record is deleted. |
| `PUT` / `GET /lsp-backup` | LSPs | `lijox-scb:v1` — an LSP's own `channel.backup` (LND's seed-encrypted SCB), keyed and signed by its node key; latest + one previous generation, 5 MB cap. |
| `GET /backup/challenge`, `POST /backup`, `POST /backup/fetch` | wallets | the wallet's encrypted state blob: a single-use nonce is signed with the wallet's seed-derived portable key (compact ECDSA over a domain-separated sha256); versioned, latest wins. Contents are AES-GCM under a key only the seed produces; the worker sees a pubkey, a size and timing. An upload whose number is not above the copy held is refused (409), and the refusal names the copy held — its number, its fingerprint and its save date (0.23.0) — so a wallet can tell its own earlier upload from another device's. |
| `POST /backup/forget` | wallets | (0.7.0) the wallet deletes its own encrypted blob — the same signed single-use challenge (action `backup-forget`), so only the key that wrote the blob can remove it; idempotent. |
| `POST /backup/meta` | wallets | (0.9.0) the encrypted copy's number and save date only, read from its unencrypted envelope — the same signed single-use challenge as `/backup/fetch` (action `backup-read`); `{found:false}` when no copy is held. A wallet compares the number with its own before it connects to its provider, without downloading the copy. The answer also carries the copy's fingerprint (0.10.0) and the registry's record of the last 8 uploads it accepted for that wallet: number, fingerprint, time (0.23.0). |
| `POST /names/claim`, `POST /names/release`, `POST /names/transfer` | LSPs | `lijox-name:v1` — a Lightning address name at the neutral host, one LSP per name, signed with the LSP's node key; a transfer (0.15.0) hands a name its LSP holds to another registered LSP, signed by the one that holds it. |
| `GET /.well-known/lnurlp/<name>` | payers | the neutral-host LNURL-pay lookup: returns the owning LSP's own answer unchanged (edge-cached 60 s); the payment callback goes straight to that LSP. |
| `PUT` / `GET /lsp-state` | LSPs | `lijox-state:v1` (0.19.0) — the `/lsp-backup` route's twin for an LSP's own encrypted state kit, which the provider builds itself so it can rebuild its box: signed by the node key, latest + one previous generation, 20 MB cap. The worker cannot read it. |
| `GET /mirror/keys`, `GET /mirror/get`, `POST /mirror/put`, `POST /mirror/delete` | the direct copy | (0.17.0) the two copies kept the same: every write carries the clock of the copy that took it, every delete leaves a 7-day tombstone, and these routes accept only the key named in `wrangler.toml` (`LIJ_MIRROR_PUBKEY`), which never leaves the node that runs the direct copy. Open challenges are never mirrored. |
| `/lsps1/channel` | — | retired in 0.15.0 (answers 410); wallets open channels through LSPS2 (JIT) at their provider. |
| `GET /health` | anyone | liveness. |

Canonical message formats are in `lij-worker/src/index.js` beside their verifiers (`canonicalRegisterMsg`, `canonicalScbPush`/`canonicalScbGet`, the name and backup digests). The adapter carries verbatim twins of the ones it signs; a change ships in both repositories in the same release.

LSP-side routes the standard also names live in the adapter, not the worker: `POST /lsps/registry/recover-close` (a wallet back with only its 12 words asks its LSP to force-close every channel held under its node key; all-or-nothing while any HTLC is in flight); the LNURL-pay rail (`/.well-known/lnurlp/<name>` at the LSP's own host, hold invoices minted on wallet-registered hashes; preimages never leave the wallet); the Black start kit holder (`/v1/kit` — every provider keeps any wallet's encrypted kit and cannot read it; the wallet repository's `docs/black-start-standard.md`); the `/recover` page, served by every provider for when the wallet's site does not open; and the watchtower (`/v1/tower/*`; a wallet's key is admitted by a voucher its own provider signs — `docs/lijox-watch-standard-r2.md`). The adapter's README describes each.

One wallet, one open copy (`docs/lijox-copy-guard-standard.md`, adapter ≥0.93.0): every provider answers `POST /lsps/registry/my-channels` (a wallet, signing with its node key, reads back only its own channels — read-only) and tells a wallet when another copy of it is open at the same time (60-s window, sessions held in memory only). A wallet holding no record of a channel stops and asks its person before connecting, instead of connecting and letting the provider's LND force-close a channel that copy does not know.

## Running your own registry

`lij-worker/` deploys with Wrangler to any Cloudflare account: create a KV namespace, put its id in `wrangler.toml`, `wrangler deploy`. The CI workflow does the same from a `CLOUDFLARE_API_TOKEN` secret and refuses to deploy if the local sign↔verify gate fails. A registry is a list; nothing in the protocol makes one registry more official than another.
